# verify-cocos, фаза 2а — проверки внутри прогона

Дизайн от 2026-09-29. Статус: на ревью.

Продолжение [2026-09-29-verify-cocos-design.md](2026-09-29-verify-cocos-design.md), §9.1–9.2.
Фаза 2б — агент отбора проверок (§9.3) — отдельным циклом после этой.

## 1. Задача

Сделать игру бота основным способом верификации: каждый критерий приёмки
игрового процесса внутри уровня проверяется прогоном без участия человека.

Для этого нужно:

- проверки вида «когда X — в течение N кадров Y», а не только инварианты;
- проверки отображения — по фактам дерева узлов и по пикселям;
- миссии, которые загоняют бота в нужный сценарий;
- покрытие: прогон знает, какие проверки реально сработали.

Следом (этап **1а**) — каталог правил ImageUncovered из документации, спек и
кода, закрытый проверками, с зелёными прогонами.

## 2. Границы

- Игра ради бота не меняется. Всё наблюдается снаружи: ECS-компоненты, дерево
  узлов, снимки.
- Тема прогонов — неон (`minimal`, основная). Painterly не проверяется; место
  под её раскладку узлов в мосте есть.
- Меню и переходы между уровнями — вне фазы (спека фазы 1, §10).

## 3. Модель проверок

`verify/bot/checks.mjs` заменяет `oracles.mjs`. Проверка — одно из двух:

```js
// инвариант — должен выполняться всегда (бывшие оракулы, логика та же)
{ id, kind: 'invariant', level: 'fact',
  check(prev, cur, events, ctx) → null | { message, data } }

// ожидание — когда X, то в течение within кадров Y
{ id, kind: 'expectation', level: 'fact' | 'pixel' | 'agent',
  when(prev, cur, events, ctx) → null | trigger,     // trigger — данные момента X
  then(cur, events, trigger) → boolean,              // только для level 'fact'
  region(cur, trigger) → { x, y, w, h },             // для 'pixel' и 'agent', мировые px
  within,                                            // кадров
  criterion,                                         // для 'agent': что судить на снимке
  history: ['2026-09-29 fact: …'] }                  // журнал переходов уровня
```

### Жизненный цикл ожидания

- `when` вернул trigger → ожидание **взведено**. Одновременно взведённых экземпляров
  одной проверки может быть несколько; повторный `when` пока ждёт предыдущий —
  новый экземпляр.
- **fact**: `then` истинно не позже `within` кадров → **подтверждено**; не наступило
  → **нарушение**, вердикт `bug`.
- **pixel**: через `within` кадров снимается вырезка `region` и сравнивается с
  эталоном. Совпала → подтверждено; разошлась → `bug`; эталона нет → вырезка на
  осмотр, прогон в статусе `needs-review`.
- **agent**: через `within` кадров снимается вырезка и кладётся на осмотр вместе с
  `criterion`. Прогон не падает; вердикт выносит агент (см. §6).

Прогон кончился раньше, чем истекло `within`, — экземпляр не засчитывается ни в
подтверждения, ни в нарушения («не дождался»), и это видно в покрытии.

### Покрытие

По каждой проверке прогон считает: взведено / подтверждено / нарушено / не
дождался. Инварианты — число проверенных шагов.

Файл прогона может требовать проверки: `"requires": ["id", …]`. Требуемое
ожидание, ни разу не подтверждённое за прогон, делает прогон непройденным
с причиной «не проверено». Молчаливого зелёного нет.

### Лестница уровней

Правило для агента, который пишет и сопровождает проверки (в скилле
`verify-cocos`, не в коде):

| Ситуация | Уровень |
|---|---|
| машинных фактов достаточно | `fact` |
| сомнение, что факты отражают вид | `pixel` |
| эталон часто ломается без бага | назад на `fact` |
| `fact` пропустил баг | поднять на `pixel` |
| проверка ходила туда-сюда | `agent` |

Пирамида: `fact` — большинство, `pixel` — меньше, `agent` — меньше всего.
Каждый переход — строка в `history` проверки с причиной.

## 4. Наблюдение за видом

### Помощник плагина `__botView`

Внедряется shim'ом, общий для Cocos, читает дерево узлов текущей сцены:

```js
__botView.node(path)        // 'Canvas/StatusBar/LivesLayout'
  → null | { active, worldRect: { x, y, w, h }, opacity, color: [r, g, b, a], children }
__botView.find(component)   // имя @ccclass
  → [{ path, active, worldRect, opacity }]
__botView.pageRect(worldRect)  // мировые px → CSS px страницы по камере канваса
  → { x, y, width, height }
```

`opacity` — итоговая, с учётом `UIOpacity` предков; `worldRect` — по
`UITransform` в мировых координатах.

### Мост проекта

Мост решает, какие факты положить в `observe().view`. Раскладка узлов — таблица
по темам в мосте: `{ minimal: {…}, painterly: {…} }`; тема берётся из настроек
игры. Для ImageUncovered (неон):

- `player.look` — `safe` / `danger` / `mixed` по прозрачности слоёв игрока;
- `lifeIcons` — число видимых иконок жизней и признаки идущей анимации потери;
- `progressBar.worldRect`, `hud.visible`.

Тему прогона задаёт поле `theme` файла прогона: мост записывает её в
настройки игры (`localStorage`) до загрузки.

## 5. Пиксельные эталоны

- Раскладка: `verify/baseline/<прогон>/<проверка>-<n>.png`, `n` — номер
  срабатывания за прогон. Seed и тема входят в прогон — эталоны детерминированы.
- Вырезка: `Page.captureScreenshot` с `clip = __botView.pageRect(region)`.
- Сравнение — `diffPng` (переезжает из `verify-web` в `shared/cdp` с тестами),
  порог по пикселю и допустимая доля — из `verify/cocos.json`.
- Расхождение → `bug`, рядом эталон, снимок, diff.
- Эталона нет → вырезка в `tmp/bot/<прогон>/baseline-new/`, статус
  `needs-review`.
- `--update-baseline [--run имя]` принимает текущие вырезки.
- Эталон разошёлся, а `start`-строка показывает изменившийся адаптер или
  сборку — отчёт говорит «эталон разошёлся после изменения X». Агент отсматривает
  пару «было/стало» и либо принимает эталон, либо фиксирует баг; решение — в
  `history` проверки.
- Вырезки не включают заливку поля: `region` — игрок, враг, иконки HUD, полоса.

## 6. Снимки для агента

`tmp/bot/<прогон>/review/<проверка>-<n>.png` + `review.json`: критерий, кадр,
trigger. Команда `/verify-cocos` требует от агента открыть каждый снимок и
вынести вердикт до того, как задача считается проверенной. Это слой `[visual]`
контура `acceptance`.

## 7. Миссии-сценарии

Миссия получает список допустимых видов краткосрочных целей и параметры:

```js
missions = {
  'capture-80':      { done: win,              goals: ['excursion', 'use-bonus'] },
  'lose-all-lives':  { done: gameOver,         goals: ['trail-bait', 'body-hit'] },
  'lose-life-trail': { done: lifeLost ≥ 1,     goals: ['trail-bait'] },
  'lose-life-body':  { done: lifeLost ≥ 1,     goals: ['body-hit'] },
  'collect-bonus':   { done: бонус собран,     goals: ['excursion'], params: { type } },
  'use-bonus':       { done: бонус применён,   goals: ['excursion', 'use-bonus'], params: { type } },
}
```

`candidates(model, mission)` фильтрует цели по `mission.goals`. Новые тактики
ImageUncovered:

- `trail-bait` — выйти в опасную зону на прогнозной траектории врага и ждать,
  пока он заденет след;
- `body-hit` — идти навстречу врагу;
- для `collect-bonus` оценка вылазок ставит бонус нужного типа выше всего.

Параметры миссии задаются в файле прогона: `"mission": { "name": "use-bonus", "type": 2 }`
или строкой, если параметров нет.

## 8. Прогон и критерии приёмки

```json
{ "title": "Столкновение врага со следом отнимает жизнь и проигрывает анимацию",
  "zone": "gameplay", "level": 0, "seed": 1, "theme": "minimal",
  "mission": "lose-life-trail",
  "requires": ["life-lost-on-trail-hit", "life-icon-loss-animates", "player-reset-to-trail-start"],
  "expect": { "verdict": "pass" } }
```

Критерий: `- [scenario] bot:lose-life-trail — …`. Критерий `[visual]` закрывается
проверкой уровня `agent` в `requires` этого прогона.

Прогон зелёный, только если одновременно:

1. вердикт совпал с `expect`;
2. каждое ожидание из `requires` подтверждено хотя бы раз;
3. нет пиксельных расхождений;
4. нет новых вырезок без эталона (иначе `needs-review`).

Снимки `agent` прогон не валят — они пункт отчёта для агента.

## 9. Отчёт и команды

```
✓ pass  lose-life-trail  кадров 612  [—]
    покрытие: life-lost-on-trail-hit 1/1 ✓, life-icon-loss-animates 1/1 ✓ (pixel),
              player-reset-to-trail-start 1/1 ✓
    на осмотр агентом: 1 снимок → tmp/bot/…/review/
```

- `run --update-baseline [--run имя]`, `run --theme minimal`;
- `coverage` — сводка: какие проверки какими прогонами подтверждаются, какие —
  ни одним.

Журнал получает записи `arm`, `confirm`, `miss` (нарушение ожидания), `shot`.

## 10. Этап 1а — каталог правил ImageUncovered

`docs/verification/rules.md` — таблица правил игрового процесса внутри уровня,
выписанных из `docs/` (бонусы, управление, темы, уровни), спек в
`docs/superpowers/specs/` и кода систем:

| Правило | Источник | Проверка | Уровень | Прогон |
|---|---|---|---|---|

Правило без проверки помечается с причиной («вне уровня — `verify-web`»).
Готовность 1а: каждое правило игрового процесса внутри уровня закрыто
проверкой, `coverage` показывает каждую проверку подтверждённой хотя бы одним
прогоном, все прогоны зелёные на неоне, спорные правила (документация
расходится с кодом) доложены инженеру.

## 11. Проверка самого механизма

- Игрушечный адаптер без браузера: взведение, подтверждение, нарушение по
  `within`, несколько экземпляров, «не дождался», `requires` без подтверждения,
  счётчики покрытия, фильтр целей по миссии.
- Игрушечная страница в Chrome: `__botView.node`/`find`, вырезка по `clip`,
  pixel-проверка с эталоном и без.
- `png.mjs` в `shared/cdp` с тестами из `verify-web`.

## 12. Совместимость

`oracles.mjs` → `checks.mjs`: бывшие оракулы становятся `kind: 'invariant'` без
изменения логики. Старое имя модуля не поддерживается — проект один, миграция
в том же плане. `lives-monotonic` получает проверку уровня, как у
`coverage-monotonic`.

## 13. Отвергнутое

- **Только пиксели или только агент для вида** — хрупко или дорого; лестница
  уровней берёт дешёвое там, где его достаточно.
- **Инструментирование игры ради видимых фактов** — нарушает «в сборке нет
  бота»; дерево узлов даёт те же факты снаружи.
- **Сравнение полных кадров** — заливка поля и анимации кистей делают его
  нестабильным; сравниваются вырезки.
