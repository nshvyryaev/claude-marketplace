# Контур приёмки — дизайн

Дизайн от 2026-08-26. Статус: согласован, переходим к реализации.

## 1. Задача

Снять с инженера необходимость контролировать результат работы агента. Система
помогает составить критерии приёмки, получает утверждение там, где оно нужно,
и обеспечивает проверку их выполнения на деле — включая то, что видно глазами.

Обкатка — на `E:\projects\word-chain`, браузерной игре-головоломке.

## 2. Что НЕ строим

Оркестрация берётся нативная. На момент дизайна Claude Code 2.1.222 даёт:

| Требование | Нативный механизм |
|---|---|
| Внешний двусторонний канал связи | `--channels plugin:telegram@claude-plugins-official`, включая relay permission-промптов |
| Продолжение работы без промпта человека | `/goal <условие>` — оценщик после каждого хода |
| Переживание rate limit и обрывов сети | `/goal` не сбрасывается на транзиентных ошибках |
| Отсутствие промптов на каждый инструмент | auto mode |
| Параллельные изолированные треки | worktrees, `claude agents`, agent teams |
| Экономия контекста | субагенты со своим окном, `--autocompact` |

Своего кода в этих местах не пишем. Он будет дублировать нативное и гнить:
Channels, `/goal`, agent teams приехали за полгода до этого дизайна.

## 3. Что строим

Два плагина в `claude-marketplace`.

```
claude-marketplace/
├── plugins/acceptance/        ядро процесса приёмки, не знает о типе проекта
└── plugins/verify-web/        движок прогона в браузере через CDP
```

Граница настоящая: для Cocos позже встанет `verify-cocos` с тем же контрактом,
а `acceptance` не изменится.

**Плагин везёт движок и хук, проект владеет только своими данными.** Проект
хранит `docs/acceptance/*.md` и `verify/scenarios/*`, больше ничего. Нарушение
этого правила в `pre-use-allow` до 0.6.0 дало силосный баг: фикс парсера `&&`
доехал до одного проекта и не доехал до другого, оставив дыру в
security-критичном коде.

## 4. Модуль `acceptance`

### Файл критериев

`docs/acceptance/<slug>.md`, frontmatter:

```yaml
---
status: draft | approved | frozen | verified
kind: feature | ui | bug | chore | data
---
```

Тело — список утверждений, каждое со способом проверки:

```
- [scenario] Игрок вводит слово с двумя изменёнными буквами — ход отклонён,
  показана причина, введённые буквы остаются на месте
- [visual] Экран отказа не использует красный цвет и не сдвигает раскладку
- [check] npm run typecheck выходит с нулём
```

### Хук `acceptance-freeze`

PreToolUse на Edit/Write. Пока `status: frozen`, файл критериев неизменяем.
Разморозка — только явной командой, с записью причины в лог.

Это единственная механическая защита от того, что агент подгонит критерий под
полученный результат. Обещания в промпте недостаточно: этот failure mode
наблюдался на практике — агент отчитывался «готово», а расхождение с заданием
находил человек, глядя на экран.

### Граница участия инженера

Зависит от типа работы:

| `kind` | Кто пишет критерии | Ждём подтверждения |
|---|---|---|
| `feature` — новая механика | агент | **да** |
| `ui` — видимый интерфейс | агент | **да** |
| `bug` | агент | нет; воспроизведение обязано быть в критериях |
| `chore` — техдолг, рефакторинг | агент | нет; критерий: наблюдаемое поведение не изменилось |
| `data` — данные, контент | агент | нет; критерий: проверка конвейера |

### Поверхность

Команда `/acceptance`: `new`, `approve`, `freeze`, `status`, `verify`.
Скилл `acceptance`: как составлять критерии, когда спрашивать человека, как
отчитываться в канал.

## 5. Модуль `verify-web`

Обобщение прототипа `word-chain/scripts/screenshot.mjs` — 133 строки на голом
CDP, headless Chrome, сценарии вида `click:Играть,word:КОТ`, перехват ошибок
консоли.

Три слоя, разной природы и разной цены:

| Слой | Что делает | Кто выносит вердикт | Стоимость |
|---|---|---|---|
| `scenario` | прогон шагов, детерминированные утверждения, ошибки консоли | машина | 0 |
| `snapshot` | пиксельный диф против эталона | машина | 0 |
| `visual` | снимки уходят в контекст агента, агент судит по критерию | агент | токены |

**`snapshot` — только защита от регрессии**, там где вид меняться не должен.
Это не способ развития проекта: при осознанном изменении интерфейса диф всегда
красный и ничего не сообщает.

**`visual` — единственный способ оценить новый интерфейс.** Инженеру снимки
уходят пакетом и с вердиктом, только после того как агент сам решил, что всё в
порядке. Не «посмотри, пожалуйста».

Клики по тексту кнопок, а не по CSS-селекторам: переживает перевёрстку.

### Снижение расходов на проверку

Сценарии помечены зонами (`home`, `game`, `stats`, `data`). Изменённые файлы
маппятся на зоны через карту в проекте, прогоняется подмножество. Слой `visual`
вызывается только для затронутых зон. Полный регресс — по команде и перед
релизом. Карта «файл → зона» уточняется по мере промахов.

## 6. Очередь

`BACKLOG.md` в проекте: задача, приоритет, статус, ссылка на файл критериев.
Правила приоритезации и порядок фаз — в `CLAUDE.md` проекта.

## 7. Порядок работ

| # | Шаг | Выход |
|---|---|---|
| 0 | `git init` в word-chain | откат, worktrees, изоляция треков |
| 1 | Bun + Telegram-канал; спайк: малая реальная задача под `/goal` в auto mode | **факты**: что нативка тянет, что рвётся. Модулей ещё нет |
| 2 | `verify-web` из прототипа: три слоя, зоны | работающий движок проверки |
| 3 | `acceptance`: файлы, хук заморозки, скилл, команда | контур приёмки |
| 4 | Одна настоящая фича word-chain целиком через цикл | проверка на деле, отчёт в Telegram |

Шаг 1 — спайк: его выход не код, а замер. После него известно по цифрам, нужен
ли собственный супервизор (сторож процесса, cooldown по лимитам, персистентная
очередь) и в какой части.

## 8. Известная дыра

Слой `visual` — это агент, оценивающий собственную работу. Заморозка критериев
сужает дыру, но не закрывает её.

Полностью закрыть можно только вторым независимым судьёй — субагентом, который
не видел, как писался код. Это стоит токенов. Решение: оставить дыру открытой
на шаге 4 и посмотреть, промахнётся ли агент на реальной фиче. Если промахнётся —
добавить независимого verifier'а.

## 9. Отвергнутые пути

**Собственный оркестратор** (плагин-супервизор со сторожем, cooldown, очередью,
guard-хуками; ~12–20 сессий). Отвергнут не по существу, а по очерёдности: без
замеров шага 1 неизвестно, какая его часть нужна. Возвращаемся к нему после.

**Универсальный каркас с конструктором модулей** (адаптеры канала, верификации,
трекера, окружения; 2–4 месяца). Отвергнут: один потребитель и один пилот.
Контракты адаптеров пришлось бы проектировать вперёд, не зная требований
второго потребителя. Оправдан, только если целиться в публичный продукт.
